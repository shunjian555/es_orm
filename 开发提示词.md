你是一名资深 PHP 架构师、Elasticsearch 专家和开源 Composer 扩展包开发者。

现在请你帮我从零设计并实现一个「Laravel Eloquent 风格的 Elasticsearch ORM 扩展包」。

项目目标：

开发一个现代化、类型安全、可扩展、生产可用的 PHP Elasticsearch ORM，整体使用体验类似 Laravel Eloquent，但底层能力必须充分发挥 Elasticsearch 的 Query DSL、Aggregation、Search After、PIT、Bulk、Alias、Reindex 等能力。

项目最终需要能够发布到 Packagist，并可以被普通 PHP 项目以及 Laravel 项目使用。

--------------------------------------------------
一、核心设计目标
--------------------------------------------------

项目定位：

「Eloquent 风格 + Elasticsearch 原生能力」的 PHP ORM。

不要简单地把 Elasticsearch API 封装成几个方法，也不要把 Elasticsearch 强行模拟成 MySQL。

设计原则：

1. Model API 尽可能类似 Laravel Eloquent。
2. Query Builder 提供流畅的链式 API。
3. Elasticsearch 特有能力必须保留。
4. 所有无法 ORM 化的 Elasticsearch DSL，都必须支持 raw DSL。
5. 尽可能使用 PHP 8.2+ 的类型系统。
6. 遵循 PSR-4、PSR-12。
7. 高内聚、低耦合。
8. 核心 ORM 不应该强依赖 Laravel。
9. Laravel 相关能力通过独立 Adapter / Integration 实现。
10. API 要稳定、清晰、容易扩展。
11. 所有核心功能必须有 PHPUnit 测试。
12. 所有公共 API 必须有 PHPDoc。
13. 不允许为了追求代码量而设计无意义的类。
14. 优先保证 API 设计合理，再实现功能。

--------------------------------------------------
六十、最重要的架构原则
--------------------------------------------------

请始终牢记：

这个项目不是“Elasticsearch HTTP Client”。

也不是“把 SQL 翻译成 Elasticsearch”。

而是：

一个拥有 Eloquent 使用体验的 Elasticsearch ORM。

因此：

Model API → 类似 Eloquent。

Query API → 简洁、链式。

DSL → 完整、可扩展。

Elasticsearch 特性 → 不应该被 ORM API 限制。

Raw DSL → 永远保留。

性能 → 按 Elasticsearch 的最佳实践设计。
